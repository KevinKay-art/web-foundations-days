# Day 8 Reflection

**The most difficult concept.** For me, it was concurrency: understanding that two valid requests can still produce the wrong result when they run at the same time. In the TicketHub design, the question “what if two people click the same seat at the same moment?” felt abstract until I traced the requests step by step. Reading a seat's status and updating it separately leaves a gap where another request can act. I made the idea clearer by drawing the two users' timelines, then combining the check and change into one conditional `UPDATE` inside a transaction. The unique constraint on `tickets.event_seat_id` added a final safeguard. I learned that a front end can improve the experience, but the database must enforce the rule.

**What I would improve in my capstone.** Feedback on my capstone pointed to testing and explaining decisions as weak spots. I would add automated tests for invalid input, duplicate requests, expired holds, concurrent seat selection, and failed or repeated payment webhooks. I would also improve the README so it explains why each design choice was made, not just what the code does. Finally, I would make errors explicit and useful, while logging enough context to investigate failures without exposing passwords or payment credentials.

**What I will learn next.** I want to study database indexing, transaction isolation, and practical ways to reproduce race conditions in tests. I also want to learn caching and message queues well enough to implement the waiting room and background workers described in this design. Then I will deploy a small project end to end with automated tests, monitoring, and documented recovery steps. Because my background is in accounting and insurance, I am especially interested in reliable systems where money and records must always add up.

**What I learned from revising this design.** Estimates need to agree with one another, and reliability claims need a test that could prove them wrong. I added acceptance tests for concurrent holds, idempotent webhooks, late payments, and worker failures, plus operational metrics that would help detect problems during a sale. These are design-level checks; they still need to be implemented and run before they can count as test results.
